# Work OS: handover

Work OS is Delpat's task system: tasks, projects, Notion-style notes, Discord and alerts, used by Om and the team from a laptop and a phone, and by Claude sessions through its MCP connector. What it is for, and which flows are agreed: `docs/PRODUCT.md`.

- Live app: https://work.delpat.in (the old Vercel copy is paused and no longer used)
- Code: https://github.com/roguetitan1703/work-os (public; no secrets in it), mirrored to Delpat-Tech/work-os
- Hosting: Delpat's EC2 box (ap-south-1), Caddy in front, the app under systemd (`work-os.service`, port 3100), own Node 22. Database: MongoDB Atlas. A push to `master` goes live by 03:00 IST: the box's nightly `work-os-update` deploys the newest master build (an Actions build, or `scripts/build-artifact.sh` uploaded to the `manual-builds` release); `sudo work-os-update` deploys at once. Work goes to `dev` first, and an agent's push to production needs the person's yes in chat, or a release Need when they are away (section 3, Claude Code hooks). Runbook: `docs/hosting.md`.

Each section below covers one feature in three parts: **Om** (what you can do in the app or on Discord), **Claude** (what Claude on claude.ai can do through the connector) and **Claude Code** (where the code lives and what to watch out for when changing it).

## 1. Setup and environment

On the box, configuration is in `/etc/work-os/env` (root:workos, 0640; template `deploy/env.template`); restart `work-os` after a change. For local development, copy the same variables into `.env.local`, which is gitignored. `.env.example` lists every variable.

| `MONGODB_DB` | database name (`workos`) | default `workos` |
| `BETTER_AUTH_SECRET` | signs sign-in cookies and hashes tokens (32+ random characters; `SESSION_SECRET` is read if missing). Sign-in is by user: `docs/auth.md` | yes |

## 2. Tasks and projects

### What a task has
A number (`#12`), title, description, project, mode (type of work), priority P1–P4, status (Not Started, In Progress, Blocked, Done, Dropped), tags, start and due dates, estimate, progress %, checklist, links, blocked reason, dependencies ("waits on #5"), subtasks (one level; see below), a repeat schedule (daily, weekdays, weekly or monthly; the next copy appears on each due date, done or not) and archived. Every change is written to the task's **history**, which records who made it: **You**, **You · Discord**, **Claude**, **Claude Code** or **System**.

### Om
- **Laptop:**
  - **Today:** schedule, current time block, overdue, in progress, blocked.
  - **Board:** columns by status, with filters.
  - **Projects:** progress per client.
  - **Task page:** edit everything inline, log progress, checklist, comments, history.
  - **Review** (`/review?view=done|activity|stale|archive|trash`, sidebar and phone Menu): Done, Activity (filter by you, Discord or Claude), Stale (untouched 7+ days, `lib/untouched.ts`), Archive (Restore on each row, with Undo), Trash (deleted tasks and notes: Restore, Delete forever). `/history`, `/hidden` and `/archive` redirect here. The weekly review, the daily routine card and per-person help text were one person's setup and were removed (2026-10-26); their old documents (reviews, ritualLogs) stay in the database, unread.
- **Quick add:** press **N** anywhere. You can type it all in one line:
  - `Send invoice @"Grant Leads" !1 #billing due:fri ~20m mode:admin`
  - That reads as: `@project`, `!1`–`!4` for priority, `#tag`, `due:`, `start:`, `~20m` for the estimate, `mode:`.
  - **Repeat:** `every:day`, `every:weekday`, `every:week`, `every:2w`, `every:month` (also `every:3d`, `every:2m`) make a recurring task; an unknown value stays in the title. Discord `/task` has a `repeat` choice; MCP `add_task` takes `recurrence`. The New task form (Shift+Enter) and the task page have a Repeats select. Recurring tasks show a small repeat icon on rows, board cards and Today rows (`lib/recurrence-options.ts` holds the choices).
- **Recurring tasks repeat on the calendar, not on completion** (Om, 18 Nov). A series is the chain of copies linked by `nextRef`; its head is the latest copy (repeats, no `nextRef`, not archived, not in the trash). On the day the head is due, in its owner's timezone, the alerts cron makes the next copy, whatever the head's status: due on the first beat after the head's due that is today or later (a series that fell behind, e.g. a head due five weeks ago, makes one copy, not a backlog; if that copy is due today, its own next copy follows on the next run, as it would have on time); start kept the same distance before due; checklist unticked; subtasks as new open ones; owner, assignees who can still be assigned (no "assigned" notice), result kind and text authors kept. History: "Next occurrence of #N" by System. A head with no due date counts from the day it was made. Unfinished copies stay open (overdue); a Dropped head goes on repeating like a done one. Repeat set to Never, trashing or archiving the head ends the series, and so does its owner leaving the organization; completing a task makes no copy (complete_task names the next one once it exists). Existing series need no migration: every head already in the database is picked up on the next run (one that fell behind gets its one copy). Tests: `tests/e2e/recurring.mjs` (cron with `?at=`). Code: `spawnDueOccurrences` in `lib/data/tasks.ts`, called by `app/api/cron/alerts/route.ts` (at most 200 heads a run, partial index `recurring_heads`). Each copy is one transaction whose first write claims the head (`nextRef` set while still null), so overlapping runs never make two copies and a failed run leaves nothing half done.
- **Subtasks** (docs/subtasks.md, #183): the task page has a Subtasks section (add a title and press Enter, tick one done, open it, × takes it out). A parent shows "3/8" on rows and board cards and its progress is the average of its subtasks (Done counts 100, Dropped is left out); a subtask shows "in <parent>" and its page says "Subtask of #N". One level only. A subtask is in its parent's project and moves with it. Completing a parent with open subtasks asks "Close the N open subtasks too?" (Close them / Leave them open). Deleting a parent takes its subtasks to the trash; restoring it brings them back.
- **Reopening a done task** restores its earlier progress. It no longer stays at 100%.

### Delpat OS import (2026-10)
- **Om:** Settings › Connections › **Delpat OS** › Link (once per person; sign in at Delpat OS and allow). Then New project › **From Delpat OS**: search your Delpat OS projects and press Import. Name, client, status and a description (focus and phases) are filled; it is Shared unless you pick Private. An imported project shows "Already in Work OS" next time. Hidden until `DELPAT_OS_CLIENT_SECRET` is set on the server.
- **Claude Code:** `lib/delpat-os.ts` (everything), `docs/auth.md` "Linking Delpat OS" (security design), `ProjectDoc.delpatOsId` (unique per organization). Env in `docs/hosting.md`. Tests `delpat-os` and `delpat-os-off`.

### Claude
`list_tasks`, `get_task`, `add_task`, `update_task`, `log_progress`, `complete_task`, `add_comment`, `update_checklist`, `list_projects`, `add_project`, `update_project`, `daily_summary`, `recent_activity`.
- **Subtasks:** `add_task` (and `apply_changes` `create_task`) take `subtasks: [{title, …}]` to make a parent and its subtasks in one call, and `parent` (a ref, or "$name" in a batch); `update_task` `parent` moves a task under another (`null` takes it out); `get_task` returns `parent` or `subtasks` (status, progress, assignees) and `subtaskProgress`; `list_tasks` takes `parent`; task answers carry `parent` ("#12 Title") or `subtasks` ("3 of 8 done"). `complete_task` on a parent leaves open subtasks open and lists them (`openSubtasks`). The tool text says when to use a subtask (a deliverable someone tracks on its own) and when a checklist item (a step the same person does inside the task); `add_task` and the server instructions say "for 2 or more writes, use apply_changes".
- **`daily_summary`** is the one call for a morning brief: overdue, due today, in progress, blocked and waiting, the next 7 days, everything completed or changed since the last workday and who did it, and per-project counts.
- **Dates** accept `today`, `tomorrow`, weekday names, `+3d`, `+2w` or `YYYY-MM-DD`.
- **Assignees** (phase 4, several per task since #165): `add_task`, `update_task` and the batch task ops take `assignees` (the whole list: 'me', emails, names or user ids; [] or null clears) and still `assignee` (one; replaces the list), only on tasks in shared projects (and only people on the list of a project shared with chosen people: every assignee must pass `canBeAssigned`); each newly added person gets the "Assigned to you" alert, someone taken off stops getting the task's alerts. `list_tasks` `assignee` matches any of them; task answers show `assignee` ("me, Bea") and `assignees` (the list). In the app: the task page's Assigned field (desktop) and row (phone) open a tick list (`components/assignee-picker.tsx`, one save for the whole list); task rows (Tasks, board, Today, project) show up to three initials (`AssigneeDots`). Stored as `assigneeIds: string[]`; tasks from before carry one `assigneeId`, which every read and query still takes (`lib/assignees.ts`: `assigneesOf`, `assignedTo`, `unassigned`, `unassignableFilter` with `unassignPull` for a project cascade, which takes off only the people who lose access) and which a task's next change moves over. `node scripts/migrate-assignees.mjs --db <name>` (dry run, counts only) then `--apply` moves every task and trash copy at once; after it has run on the box, the old-field paths can go.
- **Shared and private projects** (UI): the New project dialog and sheet have a Shared / Private choice (default Shared; help line under it). Project › Info › "Who sees it" switches it (`updateProjectAction` → `updateProject`, which cascades to tasks, notes, Claude items, history and trash, and drops other assignees when made private). Only the project's owner may switch (data layer refuses others; the choice is disabled for them). Under Shared, **Everyone** (default) or **Choose people** (tick members, Save; the owner is always on the list): `visibility: 'members'` + `sharedWith`, cascaded the same way; a "Has access" line and a "N people" badge show who sees it. The rule lives in `lib/visibility.ts` (see docs/multi-user.md "As built: sharing a project with chosen people"); assignees must be on the list (`canBeAssigned`, lib/assignees.ts), and taking people off asks first and ends their assignments, Claude tasks and waits like Shared → Private. Shared → Private asks first when someone else is assigned or has commented (`projectSharingImpact`, `projectSharingImpactAction`): they lose access, their assignments are removed, their queued or running Claude tasks in it end (`endForeignClaude` in dispatcher.ts: queued mark cleared, running one stopped with a stop job) and Claude items waiting on them stop waiting. A "Private" badge (`components/private-badge.tsx`, lock icon, `data-private-badge`) shows on private projects in the projects list, project header, task rows and pages, start-Claude picker, Tasks/Notes pickers and filters; shared ones show nothing. `scripts/migrate-ownership.mjs` now makes old projects private (owner: the first owner), so the owner shares them one by one. Tested by `tests/e2e/sharing.mjs`.

### Claude Code
- **Data layer:** `lib/data/tasks.ts` (create, update, history, recurrence, queries) and `lib/data/projects.ts`. Pages, server actions (`app/actions.ts`), MCP and Discord all go through it.
- **Types:** `lib/types.ts` (zod schemas). Stored document shapes and indexes: `lib/db.ts`.
- **History:** entries in `activity` are written by `logActivity()`; display text comes from `lib/activity-text.ts`.
- **Activity, everything that changed** (Work OS note e56029b458): `activity` also holds rows about State (`state_now`, `next_added`, `next_done`, `later_added`, `decision`), notes (`note_created`, `note_edited`: one per editor per hour), session friction (`session_ended` from end_work, `feedback` from the feedback tool; both on the project's State), messages (`message_sent`), Needs (`need_asked`, `need_answered`, `need_withdrawn`) and projects (`project_created`, `project_renamed`, `visibility_changed`). Each carries `subject {kind, id, ref?, title}` and is written by `logChange()` in `lib/data/tasks.ts` from `states.ts`, `notes.ts` (`logNote`), `messages.ts`, `needs.ts` (`logNeed`) and `projects.ts`. Rules:
  - **Placement follows the subject.** A row copies its subject's placement when written. A task's note rows carry the task's `taskId` and move with the task (`placeTasks`, trash and restore). Every other row carries `projectId` and no `taskId`, and `setProjectPlacement` moves them with the project. Need rows are also restamped by `restampTaskNeeds` when their task moves.
  - **Checked again on read.** `readableRows()` in `tasks.ts` re-reads each non-task row's subject through the door: deleted notes, another person's Orders page, and gone messages or Needs drop out. Task rows are read as before.
  - **Text.** A row holds the subject's own text, clipped to 140 characters, plus `textBy` when someone other than the actor wrote it; readers get `writtenBy`. `titleBy` (readers: `titleWrittenBy`) names who wrote a note title, a Need's ask or a renamed project's old name. A task taken out of every project gets `projectId: ''` on its Needs, and the Needs' rows lose `projectId`, so they no longer move with the old project. A message's body, a Need's answer words and a note's body are never copied.
  - **Readers.** `listActivity` takes `what` (tasks, state, notes, messages, needs, projects); its project filter returns the project's rows and its tasks' rows. It feeds `recent_activity` (`what`), Review › Activity (a What chip row), the project page and `daily_summary` (`otherChanges`). The digest's Since yesterday (`lib/alerts.ts`) reads the feed (H12: one `listActivity` read of State lines, tasks done, Needs and messages); its Monday block (`lib/monday.ts`) reads `feedback` and `session_ended` rows through it.
  - **Migration.** `scripts/migrate-activity.mjs --db <name> [--apply]` turns the last 14 days of State `log` entries into rows. It is a dry run unless given `--apply`, and is idempotent. Tests: `tests/e2e/activity-all.mjs` and the Activity checks in `leak-audit.mjs`.
- **Subtasks:** the "Subtasks" block in `lib/data/tasks.ts` (`placeUnder`, `parentFor`, `rollUp`, `moveSubtasks`, `listSubtasks`, `createTaskWithSubtasks`); trash and restore (`trashOne`, `restoreOne`, `withParent` on TrashDoc); UI in `components/subtasks.tsx` (chip, "in" line, the close question, the task page section). Stored fields and rules: docs/subtasks.md "As built". Tested by `tests/e2e/subtasks.mjs`.

## 3. Claude connector (MCP)

### Words

One list of words, used in the server instructions, every tool description and answer, the hook messages, the State card and the docs. `lib/mcp/docs.ts` carries the one-line agent version.

- **State** = a project's Now (one goal), Next, Later (found, not chased; says what it waits on), Decisions and Where. **task** = a deliverable someone tracks (#12). **Need** = one question to one person (`ask`). **Orders** = the standing rules (organisation, project, person). **Orders version** = one saved state of an Orders page (vN), with what changed and why, kept for undo. **note** = a page in Work OS; a project's notes sit on **shelves** (Overview, Designs, Runbooks, Handovers; archived notes are the Archive). **session** = one agent conversation (`start_work` gives its id). **handover** = the note a session leaves for the next. **copy** = WORK-STATE.md, written by the Work OS hook. **session state** = on, working, waiting, idle or off, reported by the Work OS hook (Claude Code) or taken from the last Work OS call (other clients). **friction** = one line on what got in an agent's way in Work OS: `feedback` while working, end_work's `friction` at the end; both go to the project's feed.
- **session name** = what a session is called on the roster, in this order: the name its person gave it (rename), the label `start_work` was given, Claude's own title for the session (`labelSource` says which), else `<project> · Claude Code` (or `<folder> · Claude Code` with no project). One name for the session, never the project's.
- **tool** = the surface a session runs in: desktop (the Claude desktop app), VS Code or terminal, from Claude Code's own entrypoint (`CLAUDE_CODE_ENTRYPOINT`: `claude-desktop`, `claude-vscode`, `cli`; `sdk-*` is a run that stays quiet, not on the roster). Shown beside the name and the model.
- **No project** = a session whose folder no project owns. It is on the roster under that heading, private to its person, and takes messages like any other session; it has no State, no Orders and no tasks. Filing the folder moves it onto the project.
- **off** = the session is not running: the worker says its process is gone, or it said nothing for 30 minutes and no worker says it runs. A session that said nothing for 10 minutes while working is **idle**, not working. Work OS never says "present now" for an off session.
- **Monday numbers** = the four counts and up to three proposals in the organization owner's Monday digest (sessions that changed files and saved State, PCs with no hooks, WORK-STATE.md edits refused and forwarded, Om's repeats); silence means keep.
- **release Need** = an approve Need asked with `release: true` (to the project's owner, options fixed by the server: Yes release (1 hour), Yes for 24 hours, No). Yes opens production on the project for its window: pushes, tags, releases and production commands pass the Work OS hook until it ends. The only approval the hook accepts in an unattended session; in an attended one (the person typed in this same main session in the last 30 minutes, not a subagent, not dispatched) the hook passes the action with a note to record the person's words as a Decision, and the agent must have their yes in chat (the hook cannot check it).
- **worker** = a Claude Code session the task dispatcher started (`<Project> · worker · #ref`; the server marks it from this PC's own worker session row, so its hooks refuse Orders edits and shell calls to Work OS, even after a resume). Not the PC's worker program (that is "the worker" on the Claude page's Computers).
- **folder** = where a session starts. A project owns folders per PC (linked in the app, or by a session with start_work `link`); the longest owned folder wins, and a worktree or subfolder of an owned folder belongs to the same project. The remote is information: it never picks the project, it only ranks the suggestions ("same remote"). **unfiled** = a session in a folder no project owns: it asks its person once which project it is for, then files the folder (link), creates the project first (`add_project`), or marks the folder **not Work OS** (`not_work_os`, per person, undone in Claude › Setup › Computers). Never "Lobby" in agent-facing text (a design word).
- **Declutter** = the tidy-up Work OS proposes when a project grows (`declutter` tool, project ⋯ › Declutter, a declutter Need). **archived line** = a Next or Later line taken off the State into its archive (`archive_line`); nothing is deleted, and the person can put it back from the State card.
- **Retired:** "Claude item" (say a Later line, a Next line, a task or a Need), "work state file" (say the State, or the copy), "transfer note" (say handover), "boilerplate" (say Orders, or "the note the dispatcher's sessions read first"). WORK-STATE.md is only ever "a copy of the State", never the work list.
- **Asking:** while the person is in the conversation, ask them in chat and record the answer as a Decision (`save_state` `add_decision`). `ask` (a Need) only when they are away (the session runs alone, or they have gone quiet on a blocking question) or the question is for someone else. One exception (H8, changed 19 Nov): a push, tag or release to production, or a production command, needs the person's yes in chat while they are present (record it as a Decision), and a release Need only when the session is unattended (no prompt from the person for 30 minutes), dispatched, or a subagent's call; a release Need still works everywhere.
- **Kept honest by `tests/words-check.mjs`** (`npm run check:words`, also run by `prebuild`): the instructions (`serverInstructions()`, what the server really sends) stay under 2,500 characters for a Claude Code key and for the connector; the retired words and WORK-STATE.md as anything but a copy fail the build in agent-facing text (lib/mcp, lib/mail, worker, the Claude page, the State card, states/dispatcher/notes). Allowed WORK-STATE phrases are `STATE_FILE_OK` in `lib/mcp/docs.ts`. The header prefix "Copy of the Work OS state, version N." and the "# Work state:" line are parsed by installed hooks: do not reword them.

### Claude
- **Every write is attributed to Claude** in history. It records the key's owner: a teammate's key shows as "Claude · <name>".
- **The connector acts for the key's owner in their organization.** It sees shared work plus that person's private things, nothing else. MCP field changes from phase 2 are listed in `docs/multi-user.md` ("As built: phase 2"):
  - `waitingOnOm` became `waitingText` + `waitingOn`, and the `waiting_on` arg was added;
  - `visibility` was added;
  - `by` holds names for other people.
- **The connector tells Claude how to behave:**
  - Refer to tasks as `#12`.
  - Add a short note to writes.
  - Use `log_progress` and `complete_task`.
  - Use `apply_changes` for multi-step work and `get_project` for overviews.
  - Update an existing note before creating a new one.
  - **Needs (ask one person one thing):** `ask`, `needs`, `withdraw_need`. While the person is in the conversation, the agent asks in chat and records the answer (`save_state` `add_decision`). An agent that needs ONE person who is away (or is not in the conversation) to decide, approve, do or chase something, or has a question for someone else, calls `ask` instead of writing "waits on Om" in text. **No tool, key or OAuth client answers a Need**: only the addressed person does, in the app (Today's "Needs you" block on the laptop and the phone, or the project's Needs tab). The asker reads the answer with `needs`. `ask` refuses a `to` who cannot read the project; at most 10 open Needs from one asker to one person in one project (each project counts on its own, Om 19 Nov); a second open Need of the same kind on the same task replaces the first. The task then shows "Needs <name>: <ask>" instead of its percent, and is never "stalled". The asker's word is set by the server, never by an argument: `chat` only for a claude.ai app that signed in through OAuth (its key id starts `oauth_`; it may run unattended), `agent` for every key, including a static Claude chat key. At most 20 Needs created from one asker to one person in an hour (any status, all projects together), and a replacement of a Need alerted under 10 minutes ago sends no second alert. `withdraw_need` takes back only a Need of the same word and, where recorded, the same session and key; a person's own Needs and review Needs are never withdrawn by an agent.

## 10. Login and security

Full details: **`docs/auth.md`** (sign-in, roles, invitations, keys, the one-time migration, environment).

  sessions, keys, computers and Claude claims in that organization; docs/multi-user.md "As built: phase 4").

- **Security headers (red-team R2-01):** every page gets a Content-Security-Policy with a fresh nonce from `proxy.ts` (`pageCsp`): scripts only with the nonce (`'strict-dynamic'`), styles `'unsafe-inline'` (React style attributes, sonner, BlockNote), images and media from any https address, never framed.

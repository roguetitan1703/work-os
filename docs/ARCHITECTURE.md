# Architecture: owned questions

Some questions about a Claude session have exactly one owner: the module that answers them. Code that needs an answer calls the owner. A new answer anywhere else is a rejected change (AGENTS.md). `npm run check:owners` (part of `npm run check`; `prebuild` runs it too) enforces it: `tests/owners.json` lists, per guarded question, the patterns that answer it by hand, the owner files, and how many each other file has today, a baseline that only goes down.

"Owner today" is what `dev` has (read at 0a02359 and checked again at 8062274, 22 Nov 2026). Where there is no single owner, the cell says so and names the copies. "Target owner" is where the answer moves; M0 to M6 is the migration order of the harness audit of 22 Nov 2026 (Work OS note 5e073d193f). A target owner is built only when its row here says so.

## The guard

`tests/owners.json` has one entry per guarded question: session, placement, alive, holdings, delivery, claude-process, facts, and typed-facts (a `machine`, `account` or `model` string in a `lib/mcp` tool schema or in `lib/types.ts`; no file may add one). A failure names the file, the line and the owner to call. Comments, imports and `export … from` lines are not counted; a pattern can still match a line that answers nothing, and that line stays in the baseline. The patterns catch literal copies of an answer. A copy reworded so that no pattern matches it (another name, a helper, or a line the parser misreads, such as one after a regex literal with a quote in it) passes the check; the reviewer catches those.

The baseline only goes down. In a git checkout the check compares `tests/owners.json` with its copy at the merge-base of `HEAD` with `origin/dev`, with the upstream of `dev` and with `dev`, and, in the pre-push hook, with the commit the remote has for the pushed branch (in CI, the commit before the push). A higher count, a file the base does not list, or a missing baseline fails. A count below the baseline fails too, until `npm run check:owners -- --update` locks it in. After a `git mv`, `npm run check:owners -- --rename <old> <new>` carries the count. A shallow clone, a clone where no base has a merge-base, or a base that has the check but no `tests/owners.json` fails instead of skipping the comparison.

A question changed together with its row here is measured again only for what it adds: the base's own question, run over the new code, may not count more than the base allowed, and a question the base counts answers for cannot be removed. A file that becomes an owner or a target owner of a question is named in a line this change adds here. A target owner is exempt only while its file does not exist: the commit that creates it moves it into the owners and rewrites its row here.

The files listed in `.githooks/gate-files` (`package.json`, `.npmrc`, `tsconfig.json`, `tsconfig.check.json`, `.githooks`, `scripts/check-links.mjs`, `tests/*-check.mjs`, `node_modules`) are the gate itself, and each checkout runs its own copy of them, so a branch could loosen them and still print ok. The pre-push hook names the gate files a push changes (`pre-push: NOTE:`), against the list in the remote's commit plus `.githooks`, `package.json` and `node_modules`; it refuses a commit that tracks a file under `node_modules`, and a run that printed no `check:owners ok` line. `check:owners` prints a `NOTE:` line for the same files against each base.

The guard catches mistakes made by agents, not a determined branch author. A merged edit to `.githooks/pre-push` takes effect on the push that carries it, and a gate file changed to print a fake ok line passes; the `NOTE:` lines make such changes visible, and the reviewer's diff of the gate is what stops them (and CI, once it is part of the gate). The reviewer reads that diff: `git diff dev... -- package.json .npmrc tsconfig.json tsconfig.check.json .githooks scripts/check-links.mjs 'tests/*-check.mjs' node_modules`.

Changing this table: a new question needs your person's yes. A change to a guarded question (its owners, target, folders or patterns) changes its row here in the same commit, or the check fails; to measure that question again, delete its baseline and run `npm run check:owners -- --init`.
